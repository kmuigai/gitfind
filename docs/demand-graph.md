# The Demand Graph

One row per act of visitor intent on gitfind.ai, stored in `demand_events`
(migration `006-demand-events.sql`).

**Why it exists:** GitFind's catalog data describes the *supply* side of open
source — what exists and how fast it is rising. It says nothing about the
*demand* side: what people actually came looking for. A search string is the
purest form of that signal, and it evaporates the moment it is typed unless
it is written down. This table writes it down, in GitFind's own database,
from day one — before any distribution push (SEO, digests, partnerships)
sends real traffic. Intent data collected late is intent data lost; a
competitor can scrape GitHub, but nobody can retroactively observe what
GitFind's visitors searched for last month. That is the moat this table
builds.

This is **not** pageview analytics. Vercel Analytics already counts
pageviews, referrers, and geography, and continues to. The Demand Graph
records only the events that express intent, at the granularity that makes
them joinable to the catalog.

## The taxonomy (v1 — 4 event types)

| event_type | Meaning | Key fields | Wired in v1 |
|---|---|---|---|
| `search` | A search was executed on the search results page (`/search?q=…`), including searches with zero results. | `query` | ✅ search page |
| `project_click` | A project result was clicked — from the search results grid or the SearchBar dropdown. | `target` = `owner/name`, `query` when from search | ✅ search page + SearchBar |
| `category_view` | A category page (`/category/<slug>`) was viewed. One per page mount — it marks *interest in a category*, not a raw pageview count. | `target` = category slug | ✅ category pages |
| `digest_click` | A link in the email digest was clicked. | `target` | Schema only — digest links do not route through a tracked redirect yet; the type exists so the table never needs a taxonomy change when they do. |

## What is captured — and what is deliberately not

Captured per row: `event_type`, `query` (the raw search string, capped at
200 chars — the query *is* the asset), `target` (project key or category
slug), `referrer_page` (the on-site path the event happened on), and
`session_hash`.

Deliberately **not** captured:

- **No PII.** No emails, no names, no account ids — the API route rejects
  any payload field outside the documented shape, so PII cannot be
  smuggled in even by a buggy or malicious client.
- **No IP addresses** and **no raw user agents** are stored. (Not even a
  coarse device class in v1 — add it as a schema change on purpose if a
  real question ever needs it.)
- **No cross-day identity.** `session_hash` is a hash of a random
  per-browser token and the UTC date (see `lib/track.ts`). It groups one
  browser's events within a single day — enough to tell "searched, then
  clicked" apart from "searched, then left" — and rotates daily, so it
  cannot follow a person across days.
- **Do Not Track is honored.** When `navigator.doNotTrack` is set, the
  client sends nothing at all.

## The write path

`lib/track.ts` (fire-and-forget `sendBeacon`, keepalive-fetch fallback —
tracking never blocks or breaks a page) → `POST /api/events` → strict
validation in `lib/demand.ts` (event-type allowlist, field allowlist,
length caps) → insert via the **service role** into `demand_events`.

Row Level Security mirrors `api_access_requests` (migration 004): the anon
role has an INSERT-only policy and there is deliberately **no SELECT
policy** — demand rows are write-only from the public side. Kayu reads
aggregates in the Supabase dashboard (Table Editor / SQL).

## Questions this answers later

- **Top unmet searches** — `search` rows whose session shows no
  `project_click` (or whose query matches nothing in the catalog): the
  projects and topics people want that GitFind does not surface yet.
  This is a discovery backlog, generated by visitors for free.
- **Trending queries, week over week** — query volume by week, joined
  against the catalog to see demand arriving before supply does.
- **Most-clicked projects per category** — clicks joined to the category
  each project belongs to: which entries actually earn attention, not
  just impressions.
- **Category demand vs. supply** — `category_view` volume against the
  number of scored projects per category: where to point the pipeline.

## Retention

Raw rows are the asset — do not delete them casually; a search string from
2026 is unobservable in 2027. When volume makes raw scans slow, aggregate
**monthly** into rollup tables (query × week counts, clicks × project ×
week) and keep the raw rows archived alongside, the same point-in-time
discipline as the archive snapshots (Directive 1).
